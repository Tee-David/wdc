# Marketing site: real-world journey review

Review date: 6 October 2026. Source baseline: main at `79bf4d7` and the current working files inspected during this review. This is a proposal for owner review, not an implementation checklist or a release certificate. No application files, provider settings, database records or messages were changed.

## Evidence and boundaries

Reviewed the current README design rules, public Contact, Start, service detail and meeting entry pages; shared contact/custom form rendering; all six service question inventories; onboarding service choice, draft/save/resume/reset and help controls. Compared `plans/onboarding-flow-improvements-plan.md` and `plans/onboarding-service-experience-plan.md` to the actual source. Those plans remain proposals: their presence does not mean their changes have shipped.

Findings below are source-confirmed behaviours and wording. This audit did not run a browser walkthrough, send an enquiry, reserve a meeting, submit a brief, send a resume email, or validate deployed provider configuration. Mobile spacing, contrast, popover clipping, screen-reader announcements, custom-cursor behaviour in a native dialog, and live delivery remain unverified here. Existing tests and comments are useful pointers, not fresh measurements.

## What should remain

The public pages reuse the navy `wk-hero`, existing typography and black/white labelled button pair. Contact offers enquiry and scheduling paths (`frontend/app/contact/page.tsx:91`), and `/meet` explains that an enquiry is also possible. Booking has a no-times fallback linking to Contact, a timezone selector and rechecks availability at confirmation (`frontend/components/meetings/booking.tsx:47-50`). Preserve these alternatives rather than inventing another intake channel.

`/start` is already a short four-screen enquiry, backed by the same contact endpoint as `/contact`, with optional budget, timing and phone (`frontend/components/start/start-form.tsx:16-37`). The detailed six-service onboarding is a separate brief. Keep this separation: a first-time visitor should not have to complete a full brief to ask whether the studio can help.

The brief already has conditional questions, reversible “please advise” support, a shared press-to-open Tip and designed searchable pickers. SelectField implements keyboard movement, selection and Escape (`frontend/components/onboarding/select-field.tsx:29-33`); Tip uses a real button and viewport-aware placement (`frontend/components/onboarding/tip.tsx:18-31,57-70`). Extend these existing controls only where a question needs explanation. Essential instructions stay visible; specialist background can be optional help.

## Six-service help, without six redesigns

| Service | Client's likely uncertainty | Minimal wording/help proposal |
|---|---|---|
| Branding | Logo versus brand guide; where a “mark” will work | Ask where people will see/use the logo. Provide one simple labelled guide/logo usage example, clearly an illustration, not fabricated client work. Optional colour names/swatches remain preferences. |
| SEO | Search Console, Analytics, CMS access and “outrank” | Ask what they want people to find and whether anyone manages the website. Explain access as inviting the studio through the tool; never request passwords in the brief. Clients can say they do not know competitor rankings. |
| Website | Domain versus hosting; content readiness and maintenance | Define web address and where the site lives beside the existing question. Keep the existing ownership/cost disclosure (`lib/onboarding.ts:379-382`); allow help identifying what they already own. A content-not-ready answer should lead to a quoted help option, not stop the form. |
| Mobile app | Store accounts, platform and backend | Explain iPhone/Android and existing app/server information in ordinary words. Preserve the existing paid-store-account ownership disclosure (`lib/onboarding.ts:397-404`) and “please advise” route. Do not turn this into a technology selection quiz. |
| Software | Integrations, data location and compliance | Start with the manual task and who does it. Existing examples of spreadsheets, paper and current systems are useful (`lib/onboarding.ts:413-419`). Explain “systems it must talk to” using one familiar example; known legal/data requirements are optional information, not a demand to write a policy. |
| Social media | Handles, content ownership and secure account access | Keep conditional platform handles and business outcome choices (`lib/onboarding.ts:434-465`). Explain shared account access without collecting login credentials. Offer a concrete content-format example only where a client needs it, using an optional panel. |

Do not ask every visitor all six briefs. Do not add payment, analytics dashboards, recommendation engines, testimonials, pricing promises or new onboarding stages to solve these copy problems. Existing real work and real testimonial sources are the trust evidence; this audit does not independently authenticate them.

## Real-world acceptance journeys

A visitor who knows the service can move from its detail page to a preselected short enquiry, edit the topic, decline optional budget/phone, and submit using keyboard or touch. Persisted success, submission rejection and network failure must show distinct messages; failure keeps answers and focuses useful guidance. A visitor who is uncertain can ask for advice without choosing a technical implementation. A visitor preferring conversation can choose date/time/timezone, see no-slot or provider-unavailable recovery, and return to enquiry without losing unrelated work.

A client filling each of the six briefs can answer without specialist vocabulary, change a deferral to a real answer, reveal only applicable follow-ups, and complete the review using all three existing form styles. The colour editor, if approved, accepts zero through five preferences, remains optional and preserves legacy saved text. Long company names, email addresses and help copy fit without widening the page.

A slow/offline client sees accurate local-versus-server save status, can copy a usable link when email is unavailable, and cannot accidentally overwrite newer answers with an older response. Start over during an in-flight save either completes consistently or leaves recoverable answers with a clear retry. Expired/used/submitted resume links explain what happened and provide one usable next action. A submitted brief is confirmed separately from message delivery.

For each journey, review 320/375px phones, tablet and desktop in light/dark, plus keyboard-only and reduced motion. Verify visible focus, 44px targets, icon centering, label/helper placement, viewport-bounded menus/tooltips, preserved native phone scrolling and dialogs with a visible cursor. Measure actual text/control contrast against rendered grounds rather than infer it from token names. Confirm form states with deterministic provider/network fixtures; do not send live emails or make live bookings just to demonstrate an error state.

## Reconciliation before implementation

The two onboarding proposals already cover compact service choice, truthful draft status, reset/resume, plain-language service help, optional colour preferences and post-invite profile setup. Keep those requirements in their existing plans and reconcile the wording/priority findings above into one owner-reviewed scope. Optional post-invite photo/theme setup is account onboarding; it should not be inserted into the first enquiry or made a condition of submitting a brief. Current global dark default (`app/layout.tsx:155`) is a standing behaviour, not evidence that system theme preference has shipped.

No implementation checklist is created by this review. Once the owner approves the reconciled scope, the next artifact should identify only the chosen fixes and their release evidence. The most useful first change is reliable draft/reset/message feedback, followed by the shared language/help corrections and a measured responsive review of the existing surfaces.
