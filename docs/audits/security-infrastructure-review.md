# Security and infrastructure review

6 October 2026. Read-only source review; proposal, not an approved implementation checklist. No database/provider mutation, penetration testing, deployment or credential inspection was performed. Severity describes the code risk, not a demonstrated production breach.

## Priority findings

| Priority | Finding and evidence | Practical fix and acceptance check |
| --- | --- | --- |
| High | **DNS rebinding remains possible in public URL tools.** `frontend/lib/fetch-page.ts` checks DNS answers, then ordinary fetch resolves the name again; its comment explicitly documents the gap. An attacker-controlled hostname can change between validation and connection and reach an otherwise blocked address. Existing scheme/port/IP/redirect/deadline/byte checks help, but do not pin the socket. | Pin connections to a validated public address, preserving TLS hostname verification, or move these fetches behind an egress service that blocks private destinations. A controlled test hostname that changes from public to private must never reach the private test listener; repeat for redirect hops and IPv6. Do not test against real metadata services. |
| High | **Private form files have no per-submission ownership proof.** `frontend/app/api/forms/[slug]/upload/route.ts` issues keys under a common form prefix without a draft/session grant. Submission `frontend/app/api/forms/[slug]/route.ts` and `frontend/lib/forms/custom-def.ts:231` accept any file key beginning with that prefix. `frontend/lib/onboarding-files.ts` then signs downloads from those accepted answers. A submitter who learns another key in the same form can attach someone else's file; unknown keys can also be presented as completed uploads. This is conditional on learning a key, not evidence that keys are publicly listed. | Persist a short-lived upload grant bound to a draft/submission cookie and object key. Finalize after checking R2 existence, measured bytes/type and grant ownership; accept only finalized grants. Tests: another submission's key, fabricated key, unfinished upload and repeated attachment fail; the legitimate retry succeeds. |
| High | **Claimed upload limits do not constrain the PUT body.** `frontend/lib/r2.ts:183` signs `content-type;host` with `UNSIGNED-PAYLOAD`, while onboarding/custom routes validate only the browser's declared size. A client can claim a small file and PUT a much larger body. Onboarding records size before upload; media completion uses HEAD but merely records an oversized object as a successful upload (`frontend/lib/admin/media-actions.ts:110`). Content type also does not prove actual file contents. | Enforce a storage-supported upload limit where possible and validate measured size at completion; quarantine/delete rejected uploads and never expose them as accepted attachments. Bound per-draft counts and clean abandoned objects. Test a falsely declared oversized file, MIME-spoofed file and expired grant without placing large real files in production. |
| Medium | **Approval is not tied strictly to the exact reviewed version.** `frontend/lib/portal/actions.ts:68` substitutes latest when the version is missing and rejects only `seen < latest`; future values and NaN pass. Approval then changes mutable store state, rather than writing an immutable exact-version approval record. This lets a client's request bypass the stale-view check. Ownership checks correctly stop another client's deliverable. | Require an explicit finite integer equal to the current shared version, and persist actor/version/time together. Test missing, malformed, stale, future and current versions; only current succeeds. Concurrent version sharing must prevent signing the previous state. |
| High for financial state; Medium elsewhere | **Generic store writes can lose concurrent changes and acknowledge before durability.** `frontend/lib/admin/persist.ts` blindly replaces a JSON record on conflict without comparing its prior revision. Portal actions schedule `persistSoon()` and return success before persistence completes. Two instances editing one record can overwrite each other, and a failed deferred write can leave an approval toast unsupported by persisted truth. | Await durable writes for user-visible mutations; use expected revisions/conditional updates for shared records, prioritizing financial and approval flows. Two independent instances editing the same record must produce a conflict or safely merged result; induced DB failure must not return Saved/Updated. Do not replace the whole persistence architecture merely for cosmetic edits. |
| Medium | **General admin authorization is weaker than Users authorization.** `frontend/lib/admin/guard.ts:24,59` relies on the session role; `frontend/lib/users/authorize.ts` also confirms an active owner row, and support access revalidates actor/session/target. `frontend/lib/users/manage.ts` already revokes sessions on role/deactivation changes, which materially reduces exposure. This is a defense-in-depth gap, not a proven bypass with the present auth adapter. | Revalidate active persisted role in the shared request authorization boundary, retaining development-only capture separation. Real-session tests: revoked, deactivated, demoted and absent accounts fail all representative writes, downloads and direct page requests; database failure fails closed. |
| Medium | **Abuse controls are per-instance and incoming webhook rejection writes are unbounded.** `frontend/lib/rate-limit.ts` and `frontend/lib/auth.ts` explicitly use instance memory. `frontend/app/api/paystack/webhook/route.ts` synchronizes the store before verifying a signature, then persists a provider event for every bad signature. Distributed traffic can consume database/storage work without a valid provider signature. | Use a shared budget for expensive public actions and edge/body limits for webhook ingress; authenticate before loading mutable business state where possible. Aggregate/sample rejected-signature evidence rather than making one unlimited durable row per request. Tests must show separate workers share the expensive-action limit and unsigned bursts cannot grow the ledger indefinitely. |

## Infrastructure and release gaps

- **Schema readiness:** code expects migrations 0034–0037. `frontend/lib/system/migrations.ts` reports pending files, but individual feature routes may still attempt missing tables. Match the exact deployed commit to applied migration names before enabling Users/Meetings/Paystack features; test an unapplied-schema environment shows setup guidance and blocks writes. This review did not query production migration state.
- **Application recovery is only a proposal:** `plans/backup-and-restore-plan.md` and the `/backup` artifact do not establish automatic backups or a tested restore service. Define a recovery window, private encrypted archive retention, off-host/provider recovery ownership and a successful isolated restore drill before claiming recovery is operational. Preserve current owner access; do not restore credentials, stale invitations, sessions or payment-provider effects through an application archive.
- **Scheduling is currently once daily:** `frontend/vercel.json` declares a single daily endpoint; `frontend/app/api/cron/daily/route.ts` correctly fails closed with a timing-safe secret check. This cannot itself provide precise meeting reminders or prove configured Daily/Weekly/Monthly backup jobs. Add a scheduler only when the chosen cadence/runtime requires it, with durable claims, dedupe, missed-run reporting and recipient-controlled notifications. Live scheduler plan, execution history and alert delivery were not inspected.
- **Deployment workflow is useful but not a complete release gate:** `.github/workflows/deploy.yml` serializes production deploys, checks current main, avoids duplicate native/API deployment and polls final deployment state. It does not run the repository's targeted security/role checks before deployment or verify canonical authenticated journeys afterward. Add bounded automated source checks and a canonical smoke check; reserve database-mutating lifecycle tests for an explicitly isolated test database. Provider account permissions, protection settings, quotas and currently deployed SHA remain unverified.
- **CSP permits inline/evaluated scripts:** `frontend/next.config.ts:180` uses one broad script policy including widget origins. HSTS, frame-ancestor denial, referrer policy and source-map suppression are present. Give authenticated routes a tighter policy/nonce where practical and omit marketing widget origins there. Validate sign-in/theme/dashboard functionality and inspect effective headers on the canonical deployment before claiming enforcement.
- **Resource sizing:** `frontend/lib/db/pool.ts` verifies TLS certificates and bounds connections to eight per process, but this is not eight across all serverless instances. Check actual instance/concurrency and database connection/query-budget metrics before increasing limits. Runtime DB credentials currently support owner-triggered migrations; investigate separating migration authority from ordinary request credentials after verifying deployment provisioning constraints.
- **Operational visibility:** daily work returns partial errors, and outbound logs/security intents provide useful evidence. Confirm a persisted last-success/last-failure indicator and an actionable alert for stale jobs, unapplied schema, failing uploads and deployment lag; absence of an alert is not proof that work succeeded. No external monitoring, bucket public/private policy, lifecycle policy, SMTP logs, secret rotation or repository-wide historical secret scan was verified.

## Existing safeguards to preserve

Public sign-up is disabled; new auth users cannot request roles. Password breach checks run server-side and password resets revoke sessions. Email tokens/codes are hashed. Google admission checks stored roles. New Users access changes lock active owners, protect the last owner, revoke affected sessions and persist security notices. Support mode is scoped, short-lived and read-only, with proxy and action guards. Paystack signatures establish mode and test events cannot settle live invoices. Meetings publication defaults off; signed receipts and durable command structures are present. Upload keys/types are server-selected, URL-tool redirects are manually checked, and database TLS rejects untrusted certificates.

## Verification boundary

Findings above were traced in current source; acceptance checks are proposed, not executed. No assertion is made that production is exploited or safe. Prior integrated build/static-generation and authenticated-browser checks remain open in `docs/status.md`. The reset/recovery result reported by the root task is separate work and was not independently re-run here.
